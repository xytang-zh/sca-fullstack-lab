# 任务清单：[FEATURE NAME]

**输入**：来自 `/specs/[###-feature-name]/` 的设计文档

**前置条件**：plan.md（必需）、spec.md（用户故事必需）、research.md、data-model.md、contracts/

**测试**：下方示例包含测试任务。测试为可选项——仅在功能规格明确要求时才包含。

**组织方式**：任务按用户故事分组，以支持每个故事独立实现与测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**：可并行（不同文件、无依赖）
- **[Story]**：本任务属于哪个用户故事（如 US1、US2、US3）
- 描述中需包含精确文件路径

## 路径约定

- **单一项目**：仓库根下的 `src/`、`tests/`
- **Web 应用**：`backend/src/`、`frontend/src/`
- **移动端**：`api/src/`、`ios/src/` 或 `android/src/`
- 下方路径假设单一项目——请按 plan.md 结构调整

## 依赖与执行顺序

### 阶段依赖

- **初始化（Phase 1）**：无依赖——可立即开始
- **基础（Phase 2）**：依赖初始化完成——阻塞所有用户故事
- **用户故事（Phase 3+）**：均依赖基础阶段完成
  - 有余力则可并行推进
  - 否则按优先级顺序推进（P1 → P2 → P3）
- **打磨（最后阶段）**：依赖所有目标用户故事完成

### 用户故事依赖

- **用户故事 1（P1）**：基础（Phase 2）完成后即可开始——不依赖其他故事
- **用户故事 2（P2）**：基础完成后即可开始——可能与 US1 集成，但应可独立测试
- **用户故事 3（P3）**：基础完成后即可开始——可能与 US1/US2 集成，但应可独立测试

### 每个用户故事内部

- 测试（如包含）必须先写并失败，然后才实现
- model 先于 service
- service 先于 endpoint
- 核心实现先于集成
- 完成当前故事再进入下一优先级

### 并行机会

- Phase 1 中所有标 [P] 的任务可并行
- Phase 2 中所有标 [P] 的任务可并行（在 Phase 2 内）
- 基础阶段完成后，所有用户故事可并行开始（若人力允许）
- 同一用户故事内标 [P] 的测试可并行
- 同一故事内标 [P] 的 model 可并行
- 不同用户故事可由不同成员并行推进

## 实现策略

### MVP 优先（仅用户故事 1）

1. 完成 Phase 1：初始化
2. 完成 Phase 2：基础（关键——阻塞所有故事）
3. 完成 Phase 3：用户故事 1
4. **停下并验证**：独立测试用户故事 1
5. 视情况部署/演示

### 增量交付

1. 完成初始化 + 基础 → 基础就绪
2. 增加用户故事 1 → 独立测试 → 部署/演示（MVP！）
3. 增加用户故事 2 → 独立测试 → 部署/演示
4. 增加用户故事 3 → 独立测试 → 部署/演示
5. 每个故事的加入都不破坏前序故事

### 并行团队策略

多位开发者时：

1. 团队共同完成初始化 + 基础
2. 基础完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成与集成

## 备注

- [P] 任务 = 不同文件、无依赖
- [Story] 标签把任务映射到具体用户故事，便于追溯
- 每个用户故事应可独立完成与测试
- 实现前确认测试失败
- 每个任务或逻辑分组完成后提交
- 可在任何检查点停下，独立验证该故事
- 避免：模糊任务、同文件冲突、破坏独立性的跨故事依赖

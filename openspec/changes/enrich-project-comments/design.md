# Design: 全仓库注释丰富与完善

## Context

现状（见 proposal.md）：核心/新写文件注释已完善，但覆盖面不均 —— `spring-cloud-common` 公共层、业务服务 entity/DTO/异常/常量类、前端 `packages` 的 TS、部分配置与脚本是主要缺口。本变更为**纯注释改动**，不触碰任何业务逻辑、接口契约、依赖版本。

约束（决定写法的硬约束）：
- 注释规范：`docs/12-注释规范.md`（中文、解释 Why、Javadoc 用 `/** */`、枚举/常量 100% 覆盖、复杂逻辑 `// 1.` 步骤化）
- 后端 checkstyle（阿里规范）：行宽 ≤120、禁止魔法数字、`if` 必加大括号等 —— 注释改动不得引入违规
- 红线：禁用 `@Autowired` 字段注入等（本任务不写代码，仅需保证注释不诱导违规写法）
- 前端：`<script setup>`、`@sca/api`、JSDoc 风格

## Goals / Non-Goals

**Goals:**
- 全仓库注释覆盖率达到规范要求：公开类/方法/枚举/常量/配置项 100%，复杂逻辑步骤化
- 注释质量达到 ★★★ 及以上（关键安全/业务代码 ★★★★）：解释 Why，不翻译代码
- 每次改动仅含注释，`git diff` 可逐行审查

**Non-Goals:**
- 不重构代码、不修 bug、不调整命名（即使发现魔法数字/命名不佳，也只加注释解释，不改代码）
- 不处理 `target/`、`node_modules/`、`dist/` 构建产物
- 不修改 `docs/12-注释规范.md` 与 CLAUDE.md（除非另提变更）

## Decisions

**D1. 批处理而非逐文件串行**
- **选择**：按模块划分 6 个批次，每批一个 docs commit，批内可并行（多 agent 分文件组）。
- **理由**：166 个 Java + 27 个 .vue + 23 个 .ts 逐文件串行不可行；按模块提交保证 diff 可审查、可回滚。
- **替代方案**：全量一次性提交 → diff 过大难以 review，回滚困难，**否决**。

**D2. 公共层优先（批次 0→1）**
- **选择**：先处理 `pom.xml`/基础设施/`spring-cloud-common`，再处理业务服务。
- **理由**：公共层是学习者最先接触的底座，且被所有业务服务引用；先扫清可避免后续反复。
- **替代方案**：按"缺口最大"优先 → 各模块缺口差异不显著，且公共层影响面更大，**否决**。

**D3. 注释写法遇到行宽/魔法数字时「只注释不改代码」**
- **选择**：加注释不得为使行尾注释不超 120 字符而拆分代码；魔法数字只加行尾业务含义注释，不改命名。
- **理由**：本变更开口是纯注释，任何代码改动都会破坏 diff 可审查性与回滚性；魔法数字的业务含义用注释表达即可。
- **风险**：部分行尾注释可能超 120 字符 → checkstyle 违规。**缓解**：优先把注释放代码上方（规范 §2.3 本就要求注释在代码上方）；确需行尾时控制长度，超长则上移。

**D4. 并行执行单元以「文件」为单位**
- **选择**：每个 agent 处理一组文件（如某个包/某个 service 的全部 .java），任务清单精确到文件路径。
- **理由**：注释任务文件间无依赖，天然可并行；以文件为单位避免多个 agent 改同一文件产生冲突。
- **替代方案**：以代码块为单位 → 粒度太细、协调成本高，**否决**。

**D5. 提交粒度 = 模块，commit 风格统一**
- **选择**：`docs(注释): 为 <模块> 补充 Javadoc/注释`，遵循 Conventional Commits 与仓库既有注释提交风格（最近提交均为 `docs(注释): ...`）。
- **理由**：与仓库历史一致，便于按模块回滚。

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| [加注释时误改代码/逻辑] → mitigation：每批提交前 `git diff` 逐行审查，仅允许注释行增加；可用 `git diff -w` 辅助 | 批内小步提交，违规改动易定位回滚 |
| [行尾注释超 120 字符触发 checkstyle LineLength] → mitigation：优先上方注释；行尾注释控制在 120 内，超长上移 | 每批跑 `mvn checkstyle:check` 兜底 |
| [注释与代码不一致（过时注释）] → mitigation：生成前通读全文与调用方，删除/修正孤儿注释，禁止翻译式注释 | 自检 checklist §6.1 |
| [注释密度过高产生噪音] → mitigation：严格按规范 §4.3 禁止项（废话/翻译/情绪化注释），好命名不重复注释 | 抽查相邻文件对比 |
| [多 agent 并行改共享文件（如父 POM、公共 yml）] → mitigation：共享文件归入单一批次/单一 agent 处理，避免并发写 | 任务清单按文件唯一归属 |

## Migration Plan

1. 按批次顺序执行，每批完成后：`git diff` 审查 → 后端跑 `mvn checkstyle:check -pl <模块> -am` / 前端 `pnpm typecheck` → 提交（`docs(注释): ...`）
2. 批次间无部署依赖，可逐批推送；纯注释改动无运行期回滚风险，出问题 `git revert` 单批即可
3. 全部完成后整体跑一次 `mvn validate` + `pnpm typecheck` 收尾
